# 版本号、标签、镜像和制品追溯

发布版本必须对应一个确定的 Git 提交和一组确定的构建制品。GitHub 管理源码、标签和发布记录；容器镜像存放在 ACR，规则见[制品仓库](./02-image-and-artifact-registry.md)。

## 版本与标签

- 正式版本使用 `v<主版本>.<次版本>[.<修订版本>]`，例如 `v1.0`、`v1.2.1`。兼容性破坏提升主版本，新增兼容功能提升次版本，需要单独发布修复时增加第三段。这与[现有镜像标签规则](/zh/infrastructure/05-container-runtime)一致。
- 发布标签指向已评审的源码提交。已发布标签不移动、不覆盖；需要修正时创建新版本。
- 共用库与应用分别维护版本。应用发布记录要列出依赖库版本、数据库迁移版本和外部接口兼容要求。

## 构建制品

每日集成测试流水线从受控的 `dev` 提交构建候选制品；通过 Test 验证后，CD 将同一制品部署到 Prod，不在生产环境重新构建。镜像推送到 `balco.azurecr.io`，按[三层镜像规范](/zh/infrastructure/05-container-runtime)命名；部署时使用 `sha256` 摘要固定内容。非容器应用保留构建包的校验和。CI 的验证用产物可以存放 GitHub Actions Artifacts；正式发布记录放在 GitHub Release 或项目发布台账中，并关联长期可取回的制品位置。

## 发布记录

每次发布至少记录以下字段，保证排查与回滚时能找到实际运行内容：

| 字段 | 记录内容 |
| --- | --- |
| 源码 | 仓库、Git 标签 |
| 构建 | 流水线运行链接、工具链版本、测试与扫描结果 |
| 制品 | 镜像仓库及摘要，SHA-256 校验 |
| 部署 | 环境、目标资源、部署时间、操作者 |
| 运行 | 配置版本、数据库迁移、健康检查结果、回滚目标 |

发布负责人在部署后补齐运行结果。回滚使用上一已验证的制品与兼容配置；涉及不可逆数据迁移时，发布前必须写明恢复方案。旧制品在其生产或回滚引用结束前不得清理。
