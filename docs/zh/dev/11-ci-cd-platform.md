# CI、集成测试与 CD 流水线

Balco 使用 **GitHub Actions** 设计三种流水线：CI 负责快速反馈和质量门禁；每日集成测试流水线复用 CI 检查，再从 `dev` 构建候选制品、执行集成测试并发布文档预览；CD 负责正式部署和文档发布。分支流向为[工作分支 → dev → main](./09-git-workflow.md)，部署目标按[环境管理](./06-dev-test-prod-management.md)隔离。

| 流水线 | 触发 | 主要产出 |
| --- | --- | --- |
| CI | 工作分支向 `dev` 提交 PR，以及变更合并到 `dev` 时 | 检查结果、单元测试报告、验证用构建 |
| 集成测试 | 每日定时读取 `dev` 最新提交；需要时可手动重跑 | 候选制品、Test 验证报告、制品摘要、内部文档预览 |
| CD | 候选制品通过测试、`dev → main` PR 合并并获发布批准后 | Prod 部署记录、正式文档、健康检查与回滚目标 |

## 1. CI：质量工具与门禁

CI 在 PR 阶段尽早发现问题，检查通过后才能合并到 `dev`。合并到 `dev` 后再次运行，以确认集成分支仍能构建。CI 的构建用于验证；正式候选制品由每日集成测试流水线生成。每日构建执行同一套 CI 检查，再增加集成测试和文档预览发布，不单独维护另一套质量标准。

| 检查 | 门禁规则 |
| --- | --- |
| 编译、类型检查、格式与静态分析 | 新增错误阻断合并；已有问题登记并安排清理 |
| 单元测试 | 必需测试失败阻断合并；项目记录覆盖率要求及变化 |
| 依赖与开源许可证扫描 | 高风险依赖及许可证冲突须修复，或记录有期限的风险例外 |
| 密钥扫描 | 检出真实凭据立即阻断，撤销并轮换凭据 |
| 验证用构建与容器扫描 | 构建失败或镜像存在未处理的严重漏洞时阻断合并 |
| 文档构建与链接检查 | 文档无法构建或内部链接失效时阻断合并 |

项目在仓库中记录可在本地运行的检查命令。`dev` 的 GitHub Ruleset 将上述必需检查设为合并条件；`dev → main` 的 PR 也须通过适用的 CI 检查。扫描误报或暂时无法修复的问题按[规范例外流程](./14-team-governance.md)处理。

## 2. 集成测试：每日构建 `dev`

测试流水线每天定时检出 `dev` 的最新提交，记录完整 Commit SHA，先运行 CI 的全部必需检查，再构建可发布的候选制品并部署到 Test。容器应用推送至 ACR，记录镜像摘要；非容器应用保存构建包及校验和。

检查和测试通过后，将该 `dev` 提交对应的文档发布到**内部预览站点**，供开发与验收人员查看；发布失败则每日构建失败，不把该版本标记为可发布。发布记录包含 **Commit SHA、候选制品摘要、测试报告、文档预览地址和验证时间**。测试流水线不直接发布应用或文档到 Prod，具体文档规则见[文档即代码](./13-documentation-as-code.md)。

## 3. CD：部署与发布

发布负责人以通过集成测试的候选制品发起 `dev → main` PR。合并前核对 PR 的 `dev` 提交与测试报告中的 Commit SHA 一致；若测试后 `dev` 又有新提交，须重新测试当前提交。PR 通过评审并合并后，CD 流水线核对发布代码与已验证的提交一致、制品摘要与测试记录一致，再由应用负责人批准 Prod 发布。

CD 从已记录的 ACR 镜像摘要或构建包校验和部署，**不在 Prod 重新构建应用制品**。应用部署后执行健康检查和关键业务验证；通过后将对应发布版本的文档发布到**正式文档站点**。文档发布失败时不得将整次发布标记为完成，需修复或回滚到上一文档版本。应用检查失败时停止推进，按[版本与制品追溯](./10-version-and-artifact-policy.md)回滚到上一已验证制品。
