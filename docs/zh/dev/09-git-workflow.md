# 分支、Commit 与代码提交规范

Balco 使用 GitHub 进行研发协作。改动应能从需求或缺陷追溯到分支、Commit、Pull Request（PR）和发布版本。仓库权限与结构见[代码仓库规范](./01-source-code-repositories.md)。

## 分支规范

| 分支 | 用途 | 合并方向 |
| --- | --- | --- |
| `main` | 主分支，保存经过验证、可发布的代码 | 只接受 `dev` 的 PR |
| `dev` | 开发集成分支，汇总开发者完成的改动 | 接受开发者工作分支的 PR；验证后向 `main` 提交 PR |
| `dev-xxx` | 个人开发分枝 | 完成后合并入 `dev` |
| `feat-xxx` | 新功能 | 完成后合并入 `dev` |
| `hotfix-xxx` | 紧急缺陷修复 | 完成后合并入 `dev` |
| `docs-xxx` | 文档修改 | 完成后合并入 `dev` |

开发者从 `dev` 创建个人工作分支，`xxx` 使用简短描述，例如 `feat-report` `dev-su`。工作分支保持短期使用，合并后删除；需要继续开发时重新从最新 `dev` 创建或同步。`main` 和 `dev` 均受保护，不直接推送。日常流向为 **工作分支 → dev → main**。

## Commit 规范

一个 Commit 只处理一个明确目的。提交信息采用 `类型(可选范围): 简短描述`，范围可写模块或组件名称。按改动的主要目的选择类型：

| 类型 | 适用改动 | 示例 |
| --- | --- | --- |
| `feat` | 新增功能或用户可见的能力 | `feat: 增加导出功能` |
| `fix` | 修复缺陷 | `fix: 修复登录失败` |
| `docs` | 只修改文档 | `docs: 补充认证说明` |
| `refactor` | 调整代码结构，不改变外部行为 | `refactor: 拆分订单服务` |
| `test` | 新增或调整测试，不改变业务代码 | `test: 补充导出测试` |
| `perf` | 改善性能 | `perf: 减少重复查询` |
| `build` | 调整依赖、构建或打包配置 | `build: 固定 Bun 版本` |
| `ci` | 调整持续集成或部署流水线 | `ci: 增加测试步骤` |
| `chore` | 其他不影响功能的维护工作 | `chore: 更新代码所有者` |

如果改动对应 GitHub Issue，在提交信息末尾或正文写出 Issue 编号，例如 `feat: 增加导出功能 (#123)`；涉及多个 Issue 时在正文逐一列出。没有 Issue 时不必虚构编号。描述应说明实际变化，避免只写“update”“修改”或“WIP”。涉及不兼容变更时，在 Commit 正文说明影响和迁移方式。

提交前检查改动范围，不把密码、令牌、证书私钥、生产数据或包含内部信息的构建结果写入 Git 历史。发现误提交时，立即撤销凭据并按[密钥规范](./07-configuration-and-secrets-platform.md)处理；只在后续 Commit 中删除文件不足以消除历史泄露。

## 提交与评审规范

1. 开发者在工作分支完成代码、测试和相关文档，本地运行项目要求的检查，再推送并创建指向 `dev` 的 PR。
2. PR 描述关联工作项，说明改动范围、验证结果、配置或数据迁移影响及回滚方式。界面变更附截图；API 或数据库变更附兼容性说明。
3. 作者自检并等待必需检查通过；至少一名非作者评审。关键配置、权限、基础设施和流水线改动由对应负责人评审，可用 `CODEOWNERS` 指定审阅团队。阻断意见解决后才能合并。
4. `dev` 集成验证通过后，由发布负责人创建 `dev → main` 的 PR，记录待发布版本、Test 验收结果和发布影响；经评审和必需检查通过后合并。发布与回滚按[版本与制品追溯](./10-version-and-artifact-policy.md)执行。

GitHub Ruleset 应分别保护 `dev` 和 `main`：限制直接推送，要求 PR 评审、必需状态检查和对话解决。
